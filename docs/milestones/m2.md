## Spike S1: TLS request mode and certificates (task 1.2)

Run 2026-10-18 by the agent on Windows 11 (Dart 3.13.5, grpc 5.2.0, pointycastle 4.0.0, x509 0.2.4+3, asn1lib 1.6.5) with a throwaway script (`tool/spikes/m2_tls/bin/spike.dart`, not kept). The script builds a P-256 CA, a server certificate for `yagurad-<daemon-id>` and `localhost`, a device key and PKCS#10 CSR, and client certificates signed from that CSR. It then serves one unary method with `serve(security:, requestClientCertificate: true)` and calls it with four kinds of client, first with no trusted root on the server context and then with the daemon CA as its only trusted root.

Output:

```text
== 1. x509 0.2.4 probe
parse own server cert: ok, extensions=4
TbsCertificate.toAsn1 round trip identical: false (original 329 bytes, re-encoded 158 bytes)
re-parsing the x509 re-encoded TBS fails: Bad state: Unable to get name of ObjectIdentifier with nodes [0, 22, 72, 206, 61, 2, 1]
crypto_keys ECDSA sign: 64-byte signature (raw r||s, not DER)
== 2. CSR
x509 parses pointycastle CSR: subject=commonName=my-laptop
daemon verifies CSR signature: true
daemon signed client certificate: 361 bytes
== 3. grpc 5.2.0 serve(requestClientCertificate: true)
-- server trusted roots: none
(a) no client certificate: call ok, cert=none
(b) certificate from another CA: FAILED TimeoutException after 0:00:05.000000: Future not completed
(c) expired certificate from the daemon CA: FAILED TimeoutException after 0:00:05.000000: Future not completed
(d) valid certificate from the daemon CA: FAILED TimeoutException after 0:00:05.000000: Future not completed
-- server trusted roots: daemon CA
(a) no client certificate: call ok, cert=none
(b) certificate from another CA: FAILED TimeoutException after 0:00:05.000000: Future not completed
(c) expired certificate from the daemon CA: FAILED TimeoutException after 0:00:05.000000: Future not completed
(d) valid certificate from the daemon CA: call ok, cert=/CN=device
```

Findings:

- **(a) No client certificate: pass.** The handshake completes and the call runs with `call.clientCertificate == null`, so `Pairing.Info` and `Pairing.Enroll` can share the listener.
- **(b) Certificate from another CA: refused by TLS.** It does not get through with `call.clientCertificate` set, as D1 allowed for. The handshake fails, and the client's call never completes (here until the 5 s test deadline; the product sets call deadlines).
- **(c) Expired certificate: refused by TLS** in the same way.
- **(d) Valid device certificate: pass, but only when the server context trusts the daemon CA.** With no trusted root every presented certificate is refused. grpc's `ServerTlsCredentials` sets no trusted root, so the daemon subclasses it to add the CA (the script's `ServerCreds`).
- **Certificates with `x509`: fail.** `x509` 0.2.4 parses certificates and CSRs, but `TbsCertificate.toAsn1()` drops the extensions and corrupts the public-key OID on re-encoding, and the package has no signing API (`crypto_keys`, which it re-exports, signs only to raw `r||s`). It cannot build a CA certificate (basic constraints) or a server certificate (subject alternative names).
- **CSR in-process with `pointycastle`: pass.** A PKCS#10 CSR built from a `pointycastle` P-256 key parses with `x509`, its signature verifies, and the daemon signs a client certificate from it with a hand-written DER builder (about 150 lines: TLV, INTEGER, OID, BIT STRING, UTCTime, names, extensions; `pointycastle` `SHA-256/ECDSA` with the signature DER-encoded as `SEQUENCE {r, s}`). Dart's TLS stack accepts those certificates and SEC1 `EC PRIVATE KEY` PEM keys (row (d)).

Decision:

- **One listener in request mode** (D1's main path, as `docs/protocol.md` "Per-call authorization" describes): the daemon CA is the listener's only trusted root, so TLS refuses unknown and expired certificates, and the auth gate (D2) enforces presence, device membership and revocation per call. The port + 1 fallback is not needed, so D1's listener choice stands. The daemon-security scenario "Renewal without a valid certificate" already allows a refused handshake.
- **Certificate building:** D1's stated fallback applies. CA, server and client certificates are built with a minimal DER builder over `pointycastle` instead of `x509`. This changes D1's choice and task 1.4's dependency list, so it goes to the user as a design amendment.

## Spike S2: service, accounts and signal (task 1.3)

Run 2026-10-18 by the agent in the `elevated` workflow on a GitHub `windows-latest` runner (Windows Server 2025, `Microsoft Windows NT 10.0.26100.0`, as administrator), from the throwaway branch `elevated/m2-spike-s2` (never merged; the scripts in `tool/spikes/m2_service/` are not kept). Final run: [39132443677](https://github.com/sh1ny/yagura/actions/runs/39132443677); runs 1-6 found the problems listed below.

The setup script creates two temporary accounts, `yspk-srv` and `yspk-steam` (members of Users; `SeBatchLogonRight` granted; interactive and remote-interactive logon denied), and a directory `C:\YaguraSpike` with account-specific ACLs. It registers a WinSW service (`WinSW.NET461.exe` 2.12.0, SHA-256 `b5066b7b…dfc4f`, the binary of task 1.4) running a C# stub as LocalSystem. The stub launches the relay (`yagurad relay` from a `dart build cli` bundle, with the M1 `fake_server` as the game server) through a short-lived `launch` child as `yspk-srv`, with `LogonUserW(LOGON32_LOGON_BATCH)`, `LoadUserProfileW`, `CreateEnvironmentBlock` and `CreateProcessAsUserW` on window station and desktop `YaguraSpkSrv\Default`, whose DACL grants SYSTEM, Administrators and the account SID. A removal script then deletes the service, ends the processes, removes the accounts' rights, profiles and accounts and the directory; a final step checks that nothing is left.

Results (final run):

```text

PASS S2.2 relay and server survive service stop: service Stopped; relay alive True, server alive True
PASS S2.3 service start re-attaches, launches nothing: relay alive True, re-attach logged True
PASS S2.4 relay and server survive service restart: relay alive True, server alive True
PASS S2.5 upgrade to v2 keeps the relay; v1 yagurad.exe stays locked: service runs C:\YaguraSpike\v2\spike.exe; relay alive True, server alive True; v1 yagurad.exe locked True
PASS S2.6 yagurad signal as LocalSystem delivers Ctrl+C to the relay console: signal exit 0; fake_server saw Ctrl+C True; exit.json written True
  SteamCMD bootstrap runs: exit_code: 7, exit_code: 0
PASS S2.7 SteamCMD installs as yspk-steam on YaguraSpkSteam: launch exit 0, steamcmd exit_code: 0, installed file owner runnervm0xl3a\yspk-steam
PASS S2.8 yspk-steam cannot write C:\Windows\System32: launch exit 0, exit_code: 1, file created False
```

Removal: both profiles and accounts removed, `C:\YaguraSpike` deleted, "nothing left behind".

Checks, as task 1.3 lists them:

- **Relay as a low-privilege account on its own window station and desktop (S2.1): pass.** The relay and the server it starts both run as `yspk-srv`; the launch child breaks away from the service's job (`CREATE_BREAKAWAY_FROM_JOB` accepted).
- **Survives service stop (S2.2), restart (S2.4) and upgrade (S2.5): pass.** A service start finds the running relay through `relay.json` and launches nothing (S2.3). After the upgrade the service runs the v2 stub while the relay keeps executing v1's `yagurad.exe`, which stays locked, as D6's version directories assume.
- **`yagurad signal` as LocalSystem delivers Ctrl+C to the relay's console (S2.6): pass.** The server saw Ctrl+C, saved and exited 0, and the relay wrote `exit.json`. **No fallback is taken:** D7's fallback (the signal helper as `yagura-srv` on the relay's desktop) is not needed.
- **SteamCMD install as a second account on a separate desktop (S2.7): pass.** As `yspk-steam` on `YaguraSpkSteam\Default`, SteamCMD self-updated (first run exits 7, as `steamcmd_service.dart` already expects; the second `+quit` run exits 0) and then installed app 1007 anonymously; the installed files are owned by `yspk-steam`.
- **The SteamCMD account cannot write system directories (S2.8): pass.**

Findings:

- **Design gap: the profile must be unloaded.** In run 4 the launch child loaded `yspk-srv`'s profile and exited without `UnloadUserProfile`. The profile stayed loaded after every process of the account had ended, so it could not be deleted before a reboot (the removal script kept the account and said so). With `UnloadUserProfile` called right after `CreateProcessAsUserW` (and after the process exits for SteamCMD), the relay keeps running and the removal deletes both profiles (runs 5-7). Amended into design D7 "Launch", D10 "Account", ADR 0015 and task 9.3.
- **Implementation notes for task 9.3** (each a fault in the spike stub, found and fixed between runs):
  - `SetUserObjectSecurity` takes `PSECURITY_INFORMATION`, a pointer; passing the flag by value is an access violation (run 2).
  - `WINSTA_ALL_ACCESS` and `DESKTOP_ALL` hold no standard rights; the station and desktop handles need `READ_CONTROL | WRITE_DAC` for the DACL to be set on an existing object (run 3).
  - The relay exits with `helperFailed` (2) and writes nothing when `launch.json` lacks `format_version: 1`; its stderr is on its hidden console, so the daemon has to report this from the relay's exit code (run 5).
  - The first launch of a new account takes about 24 s (`LoadUserProfileW` creates the profile); later launches return at once. The daemon's launch timeout has to allow for it.
  - Under PowerShell 7, ADSI user properties are set with `Invoke('Put', ...)` and `CommitChanges()`; direct assignment fails (run 1).
